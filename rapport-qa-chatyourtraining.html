Authentification & Onboarding
✅ Ce qui fonctionne
  • Login avec credentials valides → redirection correcte vers /dashboard
  • Mauvais mot de passe → message "E-mail ou mot de passe incorrect." (non discriminant)
  • Compte inexistant → même message générique (pas de user enumeration via le message)
  • Injection SQL dans le mot de passe → correctement rejeté (Supabase paramétrisé)
  • Utilisateur déjà connecté → tentative d'accès à /register ou /login redirige vers /dashboard
  • Route protégée sans auth → redirection correcte vers /login
  • Formulaire inscription : password strength checker temps réel (12 car, maj, chiffre, spécial)
  • Bouton inscription désactivé tant que le mot de passe ne remplit pas les critères
🐛 Bugs trouvés
CRITIQUE Page "Mot de passe oublié" → 404
Étapes : Aller sur /login → cliquer "Mot de passe oublié ?" → la page /forgot-password retourne une 404 Next.js. Attendu : Un formulaire de réinitialisation de mot de passe. Observé : "404 — This page could not be found." La route n'existe pas. Impact : Aucun utilisateur ne peut récupérer son compte s'il oublie son mot de passe. Lien affiché dans l'UI = lien mort.
MAJEUR Message "email déjà utilisé" persiste après modification du champ email
Étapes : Sur /register, remplir le formulaire avec un email existant → cliquer "Créer mon compte" → erreur affichée → modifier le champ email avec un nouvel email. Attendu : Le message d'erreur disparaît quand l'utilisateur corrige l'email. Observé : "Cette adresse e-mail est déjà utilisée." reste affiché même après avoir tapé une nouvelle adresse. Impact : L'utilisateur pense que son nouvel email est aussi refusé → abandon potentiel.
MINEUR Formulaire vide → aucun message d'erreur visible
Étapes : Aller sur /login → cliquer "Se connecter" sans remplir les champs. Attendu : Messages de validation visibles sous les champs (ex. "Ce champ est requis"). Observé : La validation HTML5 native bloque la soumission et focus l'email, mais aucun message personnalisé n'apparaît dans le DOM. Sur mobile ou certains navigateurs la bulle native ne s'affiche pas du tout.
🔒 Risques sécurité
User Enumeration partielle sur /register Le message "Cette adresse e-mail est déjà utilisée." révèle qu'un email est enregistré dans la base. Un attaquant peut utiliser ce formulaire pour tester une liste d'emails et savoir lesquels ont un compte. Mitigation recommandée : utiliser un message générique du type "Si cet email est disponible, vous recevrez une confirmation."
💡 Suggestions
  • Créer la route /forgot-password avec un formulaire Supabase resetPasswordForEmail() — priorité maximale
  • Ajouter la validation client-side inline (sous chaque champ) pour les formulaires login et register
  • Remplacer le message "email déjà utilisé" par un message générique ou effacer l'erreur dès le premier keystroke

Dashboard & Visualisation
✅ Ce qui fonctionne
  • Dashboard se charge avec données réelles (CTL, ATL, TSB, récupération Whoop)
  • Changement de période graphique (7J/30J/90J) : les valeurs résumé CTL/ATL/TSB restent celles du jour courant (correct)
  • Calendrier hebdomadaire affiché avec statuts (Fait / Planifié)
  • Données santé Whoop affichées (HRV, FC repos, sommeil, strain)
  • Météo intégrée dans le calendrier (26°/17° pour dimanche)
  • Vue mobile (375px) : layout adaptatif, navigation bottom, contenu lisible
  • La modal "fatigue du jour" apparaît à la première visite de la journée
🐛 Bugs trouvés
MAJEUR Recharts : avertissement width(-1) height(-1) → graphiques potentiellement vides
Console : The width(-1) and height(-1) of chart should be greater than 0 (×2 à chaque chargement du dashboard) Observé : Les graphiques CTL/ATL/TSB et Récupération émettent cet avertissement à chaque rendu. Cela indique que le conteneur du chart n'a pas de dimensions CSS correctes au premier rendu. Impact : Sur certaines tailles d'écran ou lors d'un rendu SSR/hydration, les charts peuvent ne pas s'afficher. Fichier suspect : ResponsiveContainer dans les composants dashboard.
MAJEUR Double fetch des activités au chargement du dashboard
Console : "Dashboard - Activities fetched" et "Dashboard - TSS data for training load" apparaissent deux fois à chaque chargement. Cause probable : Deux useEffect déclenchés ou un composant qui se monte deux fois (React StrictMode en dev). Impact : En production, double appel API Supabase par chargement de page, frais inutiles et latence accrue. Ligne : src/app/(dashboard)/dashboard/page.tsx:279
MINEUR TSS semaine cible = 0 → "Charge TSS: 0%"
Observé : Dans le calendrier hebdomadaire : "TSS (semaine): 333 / 0" et "Charge TSS: 0%". La cible hebdomadaire TSS est à 0. Attendu : Soit une valeur calculée basée sur le CTL cible, soit "—" si non configuré. Impact : La métrique "Charge TSS" est inutilisable (division par zéro).
COSMÉTIQUE Titre de page h1 "Dashboard" (anglais) sur la page /chat et /workouts/[id]
Observé : Les pages /chat et /workouts/:id affichent <h1>Dashboard</h1> dans la barre de navigation supérieure au lieu du titre de la page courante. Attendu : "Coach IA" pour /chat, "Détail séance" pour /workouts/:id.
⚠️ UX Problématique
Aucune notification après sync réussi Après un sync Strava ou Whoop, le seul feedback est la mise à jour discrète du timestamp "Dernière synchro: il y a 0m". Pas de toast / notification de succès.
Format "Dernière synchro: il y a 0m" "0m" est une formulation étrange pour "à l'instant". Utiliser "À l'instant" ou "Maintenant".
Aucun objectif défini → encart vide "Aucun objectif défini. Ajoutez un objectif dans votre profil !" sans lien direct vers la page objectifs.
Séance du jour : "0 TSS" La séance planifiée d'aujourd'hui (Vélo 150 min) affiche "0 TSS" en charge. Pour une séance planifiée non complétée, afficher le TSS estimé serait plus informatif.
💡 Suggestions
  • Ajouter minWidth: 0 sur le conteneur des ResponsiveContainer Recharts pour corriger le warning de dimensions
  • Consolider les fetches dashboard en un seul appel ou utiliser useMemo / useCallback
  • Calculer automatiquement le TSS cible hebdomadaire depuis le CTL cible (CTL_target × 7)
  • Toast de confirmation après sync (succès / erreur) avec nombre d'activités importées
  • Ajouter un lien direct "Ajouter un objectif" depuis le widget "Prochain Objectif"

Coach IA Conversationnel
✅ Ce qui fonctionne
  • Réponse à une demande vague : contextualisée et pertinente (météo, séance du jour, conseils)
  • Injection de prompt bloquée : "je ne peux pas ignorer mes instructions précédentes"
  • Question hors scope (météo Paris) : refusée proprement, redirigée vers le sujet entraînement
  • Bouton Envoyer désactivé tant que le champ est vide
  • Historique des conversations accessible en sidebar avec titres automatiques
  • Puce "Nouvelle conversation" fonctionnelle
  • Suggestions rapides (Analyser ma forme / Séance du jour / Adapter le planning)
🐛 Bugs trouvés
CRITIQUE XSS Stored — Exécution de JavaScript via le chat
Payload testé : <img src=x onerror=alert(1)> Résultat : La dialog JavaScript alert("1") s'est exécutée dans le navigateur. Le payload est rendu en HTML brut dans la zone de messages sans sanitisation. Impact : Un attaquant peut injecter n'importe quel script : vol de cookie de session, redirection de phishing, keylogger, accès à l'API Supabase au nom de l'utilisateur connecté. Si les conversations sont partagées entre utilisateurs (historique commun), la vulnérabilité est amplifiée. Root cause probable : Le rendu Markdown des réponses IA et/ou des messages utilisateur utilise dangerouslySetInnerHTML sans passer par une librairie de sanitisation (DOMPurify, sanitize-html). Fix : Utiliser DOMPurify.sanitize() avant tout dangerouslySetInnerHTML, ou remplacer par react-markdown avec rehype-sanitize.
MAJEUR Coach IA déclare ne pas avoir accès aux données ATL/CTL/TSB alors qu'elles existent
Observé : Le coach répond "Actuellement, je n'ai pas accès à tes données de charge d'entraînement réelles (ATL, CTL, TSB)". Or le dashboard affiche CTL=45, ATL=43, TSB=-4. Impact : Les conseils d'entraînement donnés sans ces métriques sont génériques et potentiellement dangereux (risque surentraînement non détecté). C'est la proposition de valeur centrale de l'app. Cause probable : Le builder de contexte dans src/lib/openai/coach.ts ne reçoit pas ou n'inclut pas correctement les données de training_load.
MAJEUR Score de récupération incohérent entre Dashboard et Coach IA
Dashboard : Score récupération = 60 ("PRÊT", "-4.8% vs moyenne 63%") Coach IA : "ta récupération est au Vert (75%) aujourd'hui" Écart : 60% vs 75% — 15 points d'écart sur la même donnée Whoop du même jour. Impact : Le coach peut recommander des séances intenses alors que la récupération réelle est dans la moyenne. Perte de confiance des utilisateurs dans les données affichées. Cause probable : Le coach accède à une source différente ou une date différente que le dashboard (décalage UTC vs heure locale ?).
COSMÉTIQUE Tutoiement (tu) dans le coach vs vouvoiement (vous) dans l'UI
Observé : Le coach utilise systématiquement "tu" ("ta récupération", "ton planning") tandis que toute l'interface utilise "vous" ("Connectez-vous", "votre tableau de bord"). Impact : Incohérence de ton, peut paraître familier à certains utilisateurs.
🔒 Risques sécurité
XSS Stocké — Criticité maximale Le payload <img src=x onerror=alert(1)> s'est exécuté. En environnement de production, ce vecteur peut être utilisé pour voler le token Supabase de la session (localStorage), permettant à un attaquant de se faire passer pour l'utilisateur victime sans connaître son mot de passe. À corriger avant tout déploiement.
💡 Suggestions
  • Installer dompurify + @types/dompurify et wrapper tous les rendus HTML du chat
  • Investiguer lib/openai/coach.ts : vérifier que training_load (CTL/ATL/TSB) est bien inclus dans le JSON de contexte envoyé au modèle
  • Vérifier la source du score Whoop dans le contexte IA vs le dashboard — aligner sur la même requête/date
  • Harmoniser le tutoiement/vouvoiement dans le prompt système du coach

Intégrations Strava & Whoop
✅ Ce qui fonctionne
  • Strava connecté et synchro fonctionnelle (200 OK en 7.4s pour 177 activités)
  • Whoop connecté, données HRV/sommeil/strain visibles sur le dashboard
  • Bouton "Synchroniser" désactivé pendant la synchro → pas de double-sync UI
  • Lock distribué côté serveur (sync-helpers.ts) → protection contre les requêtes simultanées
  • Timestamp "Dernière synchro" mis à jour après sync réussi
  • Priorité des sources configurable (Strava vs Whoop)
⚠️ UX Problématique
Pas de feedback post-sync Le bouton redevient actif mais aucun toast/message n'informe l'utilisateur du résultat : combien d'activités importées, si une erreur s'est produite, etc.
Durée sync (7.4s) sans indicateur de progression Pendant la synchro, l'utilisateur voit juste le bouton grisé. Un spinner ou une barre de progression rassurerait.
💡 Suggestions
  • Afficher un toast avec le résultat : "177 activités vérifiées, 0 nouvelles" ou "Erreur : token expiré"
  • Ajouter un spinner animé sur le bouton pendant la synchro
  • Tester le cas où le token Strava/Whoop expire mid-session → vérifier le message d'erreur

Sécurité & Edge Cases
✅ Ce qui fonctionne
  • Routes protégées → redirection /login si non authentifié
  • UUID inexistant dans /workouts/:id → "Impossible de trouver cette séance" (pas d'info leakage)
  • SQL injection dans mot de passe → rejeté (Supabase ORM paramétrisé)
  • Injection de prompt chat → refusée par le modèle
  • Double sync bouton → protégé côté UI et côté serveur (lock)
  • RLS Supabase active → workout UUID d'un autre user → accès refusé (+ redirect login)
🐛 Bugs trouvés
MINEUR User Enumeration via le formulaire d'inscription
Observé : Message explicite "Cette adresse e-mail est déjà utilisée." sur /register. Impact : Permet à un attaquant de confirmer si une adresse email possède un compte sur la plateforme. Fix : Afficher toujours "Si cet email est disponible, vous recevrez un lien de confirmation." et envoyer un email en arrière-plan.
MINEUR Absence de rate limiting visible sur le formulaire de login
Observé : 3 tentatives de login infructueuses successives sans blocage, CAPTCHA ou délai croissant côté UI. Note : Supabase Auth applique un rate limit serveur par défaut, mais aucun feedback visuel n'informe l'utilisateur. Impact : Attaque brute-force discrète possible si le rate limit Supabase est configuré trop permissif.
🔒 Risques sécurité — Récapitulatif
[CRITIQUE] XSS Stored dans le chat IA Confirmé : <img src=x onerror=alert(1)> s'exécute. Fix immédiat requis : DOMPurify avant tout rendu HTML des messages.
[MINEUR] User Enumeration via /register Révèle si un email est enregistré. À adresser avant la mise en production publique.
💡 Suggestions
  • Installer DOMPurify : npm install dompurify @types/dompurify
  • Ajouter une Content Security Policy (CSP) stricte dans next.config.ts pour limiter les vecteurs XSS
  • Configurer des headers de sécurité : X-Frame-Options, X-Content-Type-Options, Referrer-Policy
  • Auditer tous les dangerouslySetInnerHTML dans le codebase
