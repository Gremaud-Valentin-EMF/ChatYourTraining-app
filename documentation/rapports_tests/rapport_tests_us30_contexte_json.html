1. Rappel de la user story

En tant qu'athlète, je veux que le Coach IA dispose d'un contexte frais et complet à chaque message, construit à partir de mes données réelles et injecté dans le prompt, afin que ses réponses soient personnalisées et à jour.

  • AC1 — Le contexte construit contient : date/heure courante, profil athlète (sports, seuils physio, objectif principal), état physiologique du jour (récupération, sommeil, HRV), métriques de charge (CTL/ATL/TSB) et planning (séance du jour + séances à venir).
  • AC2 — Quand une source de données n'est pas connectée, les champs correspondants sont absents/null et le Coach s'adapte sans générer d'erreur.
  • AC3 — Quand je modifie mon profil (sport, seuils, objectif), le contexte reflète les nouvelles données dès le message suivant et le Coach ajuste.

2. Architecture vérifiée — « Stateful Context, Stateless Model »

À chaque POST /api/chat, buildCoachContext(userId, timezone) (src/lib/openai/coach.ts) reconstruit un instantané JSON complet à partir de la base (profil, physiologie, charge, planning, météo), puis formatContextForPrompt() l'injecte dans le SYSTEM_PROMPT. Le modèle ne conserve aucun état : le contexte est neuf à chaque appel → l'AC3 est satisfait par construction.

Le contexte exact injecté est persisté dans chat_messages.context_snapshot avant l'appel au LLM (route.ts L110-116). Les instantanés ci-dessous sont lus directement en base : ils constituent la preuve déterministe, indépendante de la réponse du modèle.

Constat : tous les champs des sources non connectées sont null / vides (et non fabriqués). Correctif clé : recovery_status vaut désormais null quand le score est absent (auparavant forcé à « yellow »). Le Coach signale l'absence de données, n'invente aucune valeur, pose des questions et reste utile — réponse complète, aucune erreur. AC2 : validé.

Note (comportement LLM, hors périmètre US-30) — Posé dans la même conversation, le message 2 a vu le modèle répéter « VMA 14 » : il s'est ancré sur l'historique de la conversation (sa réponse précédente), bien que l'instantané injecté contînt déjà 17. La construction/injection du contexte est correcte ; ce biais d'ancrage disparaît en nouvelle conversation (cf. tableau ci-dessus). À surveiller côté UX si besoin.

Recommandation mineure (amélioration future) — Dans buildCoachContext, les requêtes objectives filtrent sur event_date ≥ aujourd'hui mais pas sur status : un objectif abandonné dont la date est future reste listé dans le tableau objectives. L'objectif principal reste correct (tri par date), donc le coaching n'est pas impacté ; ajouter .eq("status","active") fiabiliserait le contexte.
